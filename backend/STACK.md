# Backend Stack

This backend is planned as a Python API service with explicit SQL, Alembic migrations, and no ORM layer.

## Core Stack

- Runtime: Python 3.12+
- Web framework: FastAPI
- ASGI server: Uvicorn
- Production process manager: Gunicorn with Uvicorn workers
- Database: PostgreSQL
- Migrations: Alembic
- Database access: psycopg 3 with explicit SQL
- Validation and schemas: Pydantic v2
- Settings: pydantic-settings
- Dependency management: uv
- Testing: pytest
- API test client: httpx
- Linting and formatting: ruff
- Type checking: pyright or mypy
- Background jobs: Dramatiq or Celery
- Cache and broker: Redis
- Observability: structured logging, Sentry, OpenTelemetry

## Important Decisions

### FastAPI

FastAPI is the web framework for the backend. It gives us typed request and response contracts, dependency injection, OpenAPI generation, and a clean path for async request handling.

### No ORM

The backend should not use SQLAlchemy ORM, Django ORM, SQLModel, Tortoise, or similar object persistence layers.

Database access should be written as explicit SQL through repository/query modules. This keeps database behavior visible and makes transaction boundaries easier to reason about.

Preferred database access options:

- `psycopg` for direct PostgreSQL access
- `psycopg_pool` for connection pooling
- Raw SQL files or Python query constants for larger queries
- Typed row mapping at repository boundaries

SQLAlchemy may still appear indirectly because Alembic depends on it, but SQLAlchemy ORM should not be used for application persistence.

### Alembic Migrations

Alembic is responsible for database schema migrations.

Migration rules:

- Every schema change must be represented as an Alembic revision.
- Prefer explicit migration operations and SQL over autogenerated ORM metadata.
- Migrations should be reversible where practical.
- Production migrations should be safe for existing data.
- Large backfills should be split from schema changes.

Recommended migration style:

```python
from alembic import op
import sqlalchemy as sa


def upgrade() -> None:
    op.create_table(
        "users",
        sa.Column("id", sa.BigInteger(), primary_key=True),
        sa.Column("email", sa.Text(), nullable=False),
        sa.Column("created_at", sa.DateTime(timezone=True), nullable=False),
    )
    op.create_unique_constraint("uq_users_email", "users", ["email"])


def downgrade() -> None:
    op.drop_table("users")
```

Raw SQL is also acceptable when it is clearer:

```python
from alembic import op


def upgrade() -> None:
    op.execute("""
        CREATE TABLE users (
            id BIGSERIAL PRIMARY KEY,
            email TEXT NOT NULL UNIQUE,
            created_at TIMESTAMPTZ NOT NULL DEFAULT now()
        )
    """)


def downgrade() -> None:
    op.execute("DROP TABLE users")
```

## Transaction Handling

Transaction boundaries should be explicit and controlled at the service/use-case layer, not hidden inside repositories.

Good default:

```python
from psycopg import Connection


def create_user(conn: Connection, email: str) -> int:
    with conn.transaction():
        user_id = insert_user(conn, email)
        insert_audit_event(conn, "user.created", {"user_id": user_id})
        return user_id
```

Repositories should usually accept a connection or cursor from the caller:

```python
def insert_user(conn, email: str) -> int:
    row = conn.execute(
        """
        INSERT INTO users (email)
        VALUES (%s)
        RETURNING id
        """,
        (email,),
    ).fetchone()
    return row[0]
```

### Transaction Rules

- Start and commit transactions in service/use-case code.
- Keep repositories focused on SQL statements.
- Do not let repositories silently commit.
- Avoid long transactions.
- Avoid external network calls inside open database transactions.
- Use database constraints as the final source of truth for integrity.
- Make retry behavior explicit for serialization failures and deadlocks.

### Tools and Patterns

Use PostgreSQL and psycopg features directly:

- `conn.transaction()` for transaction scopes
- Savepoints for nested/partial rollback cases
- `SELECT ... FOR UPDATE` for row-level locking
- `FOR UPDATE SKIP LOCKED` for worker queues
- Advisory locks for coarse-grained application locks
- Isolation levels when a workflow needs stricter consistency
- Unique constraints for idempotency and deduplication
- Retry wrappers for deadlocks and serialization failures

For cross-system reliability:

- Use idempotency keys for repeatable API requests.
- Use an outbox table for events, emails, and jobs that must follow a committed database change.
- Process outbox rows with a background worker after commit.
- Store external provider request/response state instead of relying only on in-memory control flow.

Example outbox transaction:

```python
def place_order(conn, command):
    with conn.transaction():
        order_id = insert_order(conn, command)
        insert_outbox_event(
            conn,
            event_type="order.created",
            payload={"order_id": order_id},
        )
        return order_id
```

## Testing Approach

- Use pytest as the main test runner.
- Use a real PostgreSQL database for integration tests.
- Prefer testcontainers or Docker Compose for local database tests.
- Wrap tests in transactions when practical.
- Add specific tests for transaction behavior, locking, idempotency, and retry behavior.
- Use httpx for FastAPI endpoint tests.

## Deployment Shape

Minimal production shape:

```text
FastAPI app
Gunicorn + Uvicorn workers
PostgreSQL
Redis
Background worker
Alembic migration job
Sentry/OpenTelemetry/log aggregation
```

Application startup should not run migrations automatically. Migrations should run as a separate deploy step or release job.

## Local Database Commands

Run these commands from `backend/`.

```bash
make db-up
make migrate
make migration m="describe change"
make rollback
make db-current
make db-history
```

`make db-up` starts the local Docker PostgreSQL container using the root `.env` file described in `db/deployment.md`.

`make migrate` applies all Alembic migrations to the configured database.

`make migration m="describe change"` creates a new empty Alembic migration file.

`DATABASE_URL` can be supplied explicitly when needed:

```bash
DATABASE_URL="postgresql+psycopg://findoctor:change_me@localhost:5432/findoctor" make migrate
```
