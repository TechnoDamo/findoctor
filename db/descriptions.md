# Финансовая аналитическая платформа - черновик схемы базы данных

## Обзор

Документ описывает начальную структуру базы данных для финансовой аналитической платформы, рассчитанной на массового пользователя.

## Итоги ревью схемы

Базовая структура выглядит правильной для первой версии продукта: отдельно выделены пользователи, счета, операции, регулярные платежи, активы, обязательства и аналитические агрегаты.

Основные решения:

* `transactions` остается денежным журналом: все реальные движения денег проходят через эту таблицу.
* `liabilities` хранит сам долг или обязательство и его текущее состояние.
* `liability_types` хранит типы обязательств как справочник, а не как свободный текст.
* `financial_institutions` хранит банки, эмитентов карт, брокеров, криптобиржи, провайдеров кошельков и других финансовых провайдеров.
* Роли провайдера вынесены в отдельные таблицы, потому что один провайдер может быть одновременно банком, брокером и эмитентом карт.
* Предсказуемые платежи по долгам связываются через `recurring_transactions`.
* Фактические платежи по долгам записываются в `liability_payments` и связываются с денежной операцией.
* Кредитная карта может быть одновременно `account` и `liability`: счет нужен для банковской ленты и баланса, обязательство - для анализа долга и плана погашения.

Открытые вопросы для следующего этапа:

* Нужны ли отдельные таблицы для обменных курсов и мультивалютной переоценки.
* Нужно ли хранить историю балансов счетов отдельно от дневных агрегатов.
* Будет ли импорт банковских операций поддерживать внешние идентификаторы провайдеров и дедупликацию.
* Нужны ли семейные профили, если один финансовый профиль ведут несколько пользователей.

# Архитектурные принципы

Данные разделяются на три слоя.

## 1. Справочные данные

Статичные или редко изменяемые справочники.

Примеры:

* типы счетов;
* финансовые организации и провайдеры;
* роли финансовых провайдеров;
* типы обязательств;
* категории операций;
* частоты регулярных платежей.

---

## 2. Операционные данные

Реальные финансовые события пользователя.

Примеры:

* операции;
* переводы;
* регулярные платежи;
* активы;
* обязательства;
* платежи по обязательствам.

---

## 3. Аналитические данные

Производные метрики и агрегированные показатели.

Примеры:

* финансовые снимки на день;
* тренды расходов;
* AI-инсайты и рекомендации.

## Заметки по дизайну

Кредитные карты и кредитные счета могут появляться в `accounts`, если пользователь подключает их из банковской ленты. При этом `liabilities` остается канонической сущностью долга, а `accounts` хранит состояние счета и данные импорта.

`institution_id` используется, когда провайдер известен и нормализован. `institution_name` остается сырым резервным значением для импортированных или вручную введенных счетов, которые еще не сопоставлены со справочником.

Для крипты `account_type_id` описывает форму счета, например `crypto_wallet`, а `institution_id` указывает провайдера: Binance, Coinbase, Ledger, MetaMask или провайдера некастодиального кошелька.

# recurring_transactions

Шаблоны регулярных финансовых операций.

Это не фактические операции, а повторяющиеся паттерны.

| Колонка            | Тип     | Описание                                      |
| ------------------ | ------- | --------------------------------------------- |
| id                 | UUID    | Первичный ключ                                |
| user_id            | UUID    | FK -> users.id                                |
| account_id         | UUID    | FK -> accounts.id, счет списания/зачисления   |
| category_id        | UUID    | FK -> categories.id                           |
| liability_id       | UUID    | Nullable, FK -> liabilities.id                |
| operation_type     | VARCHAR | `income` / `expense` / `transfer` / `liability_payment` |
| name               | VARCHAR | Название паттерна                             |
| expected_amount    | DECIMAL | Ожидаемая сумма                               |
| currency           | VARCHAR | Ожидаемая валюта                              |
| frequency          | VARCHAR | `daily` / `weekly` / `monthly` / `yearly`     |
| interval_count     | INTEGER | Каждые N периодов, по умолчанию 1             |
| day_of_month       | INTEGER | Опциональный день месяца                      |
| start_date         | DATE    | Дата начала паттерна                          |
| end_date           | DATE    | Опциональная дата окончания                   |
| next_payment_date  | DATE    | Следующая ожидаемая дата                      |
| auto_generated     | BOOLEAN | Создано AI или вручную                        |
| confidence_score   | DECIMAL | Уверенность AI                                |
| is_active          | BOOLEAN | Активен ли паттерн                            |

## Заметки по дизайну

Обязательства связываются с регулярными платежами, когда платеж предсказуем или запланирован. Для этого используется `operation_type = liability_payment` и заполняется `liability_id`.

Примеры:

* Ежемесячный платеж по ипотеке -> строка в `recurring_transactions`, связанная с ипотекой в `liabilities`.
* Минимальный платеж по кредитной карте -> регулярный паттерн может существовать, но фактическая сумма может меняться каждый месяц.
* Разовое досрочное погашение долга -> регулярный паттерн не нужен; создаются только `transactions` и `liability_payments`.

## Заметки по дизайну

`liabilities` хранит объект долга и его текущее состояние. Это не регулярный платеж. У одного обязательства может быть ноль, один или несколько регулярных платежных паттернов, потому что график платежей может меняться.

`creditor_institution_id` используется, когда кредитор нормализован как провайдер. `creditor_name` остается для ручных долгов, неформальных долгов, импортированных названий кредиторов, которые еще не сопоставлены, и кредиторов, которых не нужно добавлять в справочник провайдеров.

# liability_payments

Фактические платежи по обязательствам.

Таблица связывает денежные операции с изменениями баланса долга и хранит разделение платежа на тело долга, проценты и комиссии.

| Колонка                  | Тип       | Описание                                      |
| ------------------------ | --------- | --------------------------------------------- |
| id                       | UUID      | Первичный ключ                                |
| user_id                  | UUID      | FK -> users.id                                |
| liability_id             | UUID      | FK -> liabilities.id                          |
| transaction_id           | UUID      | FK -> transactions.id                         |
| recurring_transaction_id | UUID      | Nullable, FK -> recurring_transactions.id     |
| payment_date             | DATE      | Дата платежа                                  |
| total_amount             | DECIMAL   | Общая сумма платежа                           |
| principal_amount         | DECIMAL   | Часть платежа, уменьшающая тело долга         |
| interest_amount          | DECIMAL   | Процентная часть платежа                      |
| fee_amount               | DECIMAL   | Комиссии, штрафы или пени                     |
| currency                 | VARCHAR   | Валюта платежа                                |
| balance_after_payment    | DECIMAL   | Остаток долга после платежа                   |
| created_at               | TIMESTAMP | Дата и время создания записи                  |

## Заметки по дизайну

Одна денежная операция может быть связана с одной записью в `liability_payments` и разделена на тело долга, проценты и комиссии. Для MVP, если разбиение неизвестно, можно временно записывать всю сумму в `principal_amount`, а затем уточнять данные после импорта от кредитора или ручной корректировки.

# merchants

Справочник продавцов и поставщиков услуг.

Полезен для аналитики расходов, автокатегоризации и AI-рекомендаций.

| Колонка   | Тип     | Описание                            |
| --------- | ------- | ----------------------------------- |
| id        | UUID    | Первичный ключ                      |
| name      | VARCHAR | Название продавца                   |
| category  | VARCHAR | Категория продавца                  |
| country   | VARCHAR | Страна                              |
| risk_level | VARCHAR | Индикатор риска                    |

## Заметки по дизайну

`transactions.merchant_name` хранит сырое название из импорта, а `merchant_id` указывает на нормализованного продавца, если сопоставление удалось.

# tags

Пользовательские теги операций.

| Колонка | Тип     | Описание           |
| ------- | ------- | ------------------ |
| id      | UUID    | Первичный ключ     |
| user_id | UUID    | FK -> users.id     |
| name    | VARCHAR | Название тега      |

---

# transaction_tags

Связь многие-ко-многим между операциями и тегами.

| Колонка        | Тип  | Описание              |
| -------------- | ---- | --------------------- |
| transaction_id | UUID | FK -> transactions.id  |
| tag_id         | UUID | FK -> tags.id          |

# daily_financial_snapshots

Ежедневное агрегированное финансовое состояние пользователя.

Используется для аналитики, графиков и прогнозирования.

| Колонка          | Тип     | Описание                       |
| ---------------- | ------- | ------------------------------ |
| id               | UUID    | Первичный ключ                 |
| user_id          | UUID    | FK -> users.id                 |
| snapshot_date    | DATE    | Дата снимка                    |
| total_cash       | DECIMAL | Общая ликвидная сумма          |
| total_assets     | DECIMAL | Общая стоимость активов        |
| total_liabilities | DECIMAL | Общая сумма обязательств      |
| net_worth        | DECIMAL | Чистый капитал                 |
| monthly_income   | DECIMAL | Доход за текущий месяц         |
| monthly_expenses | DECIMAL | Расходы за текущий месяц       |
| savings_rate     | DECIMAL | Доля сбережений                |

## Заметки по дизайну

Эта таблица должна хранить рассчитанные значения, а не быть источником истины. Источником истины остаются `accounts`, `transactions`, `assets`, `liabilities` и связанные платежные таблицы.
