# Финансовая аналитическая платформа - схема базы данных

## Назначение документа

Документ описывает предлагаемую структуру базы данных для финансовой аналитической платформы. Схема разделяет:

* справочники - стабильные значения и классификаторы;
* операционные данные - реальные финансовые объекты и события пользователя;
* аналитические данные - рассчитанные агрегаты и снимки состояния.

Ключевой принцип: реальные движения денег хранятся в `transactions`, а сущности вроде счетов, долгов, активов и регулярных платежей описывают контекст этих движений.

| `financial_institution_provider_types` | Связь провайдеров с их ролями | Связь многие-ко-многим между `financial_institutions` и `provider_types`. |

| `categories` | Категории доходов и расходов | Единое дерево категорий для операций. Поддерживает вложенность через `parent_id`. |
| `merchants` | Нормализованные продавцы и поставщики услуг | Помогает автокатегоризации, аналитике расходов и рекомендациям. |

| Таблица | Что хранит | Комментарий |

| `liability_payments` | Фактические платежи по долгам | Связывает денежную операцию с уменьшением долга и разделяет платеж на тело, проценты и комиссии. |
| `financial_goals` | Финансовые цели пользователя | Цели накопления, закрытия долга, покупки актива и другие пользовательские цели. |
| `tags` | Пользовательские теги | Гибкая пользовательская разметка операций. |
| `transaction_tags` | Связь операций с тегами | Связь многие-ко-многим между `transactions` и `tags`. |

# `users`

## Назначение

Хранит базовые данные пользователя и его настройки по умолчанию. Все пользовательские финансовые данные должны быть связаны с `users.id`.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ пользователя. Используется как корневая связь почти во всех операционных таблицах. |
| `email` | VARCHAR | Email пользователя. Может использоваться для входа, уведомлений и восстановления доступа. |
| `phone` | VARCHAR | Телефон пользователя. Нужен для альтернативного входа, уведомлений или локальных сценариев идентификации клиента. |
| `password_hash` | VARCHAR | Хэш пароля. В базе нельзя хранить пароль в открытом виде. |
| `first_name` | VARCHAR | Имя пользователя для интерфейса и персонализации. |
| `last_name` | VARCHAR | Фамилия пользователя. |
| `country` | VARCHAR | Страна пользователя. Влияет на валюты, локализацию, банковские интеграции и налоговый контекст. |
| `base_currency` | VARCHAR | Основная валюта пользователя для отчетов и пересчета чистого капитала. |
| `timezone` | VARCHAR | Часовой пояс пользователя. Нужен для корректных дневных агрегатов и регулярных платежей. |
| `created_at` | TIMESTAMP | Дата и время создания пользователя. |
| `updated_at` | TIMESTAMP | Дата и время последнего изменения записи. |

## Подробное описание

`users` является владельцем данных. Даже если в будущем появятся семейные профили или совместные бюджеты, пользовательская учетная запись все равно остается отдельной сущностью. Для семейного режима лучше добавить отдельную сущность вроде `households`, а не смешивать несколько людей в одной строке `users`.

# `account_types`

## Назначение

Справочник типов финансовых счетов. Отвечает на вопрос "что это за счет?", а не "кто его выпустил?".

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ типа счета. |
| `code` | VARCHAR | Стабильный машинный код, например `debit_card` или `crypto_wallet`. Используется в логике и аналитике. |
| `name` | VARCHAR | Название для интерфейса. Может быть локализовано. |
| `description` | TEXT | Описание типа счета и правил его использования. |

## Примеры значений

* `debit_card`
* `credit_card`
* `checking_account`
* `savings`
* `cash`
* `crypto_wallet`
* `investment_account`

## Подробное описание

Тип счета должен быть независим от провайдера. Например, `crypto_wallet` - это тип счета, а Binance, Coinbase, Ledger или MetaMask - это провайдеры из `financial_institutions`.

# `provider_types`

## Назначение

Справочник ролей финансовых провайдеров.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ роли провайдера. |
| `code` | VARCHAR | Стабильный машинный код роли. |
| `name` | VARCHAR | Название роли для интерфейса. |
| `description` | TEXT | Описание роли и правил классификации. |

## Примеры значений

* `bank`
* `card_issuer`
* `broker`
* `crypto_exchange`
* `wallet_provider`
* `payment_provider`
* `lender`

## Подробное описание

Провайдер может иметь несколько ролей. Например, Tinkoff может быть банком, брокером, эмитентом карт и кредитором. Поэтому роли вынесены отдельно и связываются через `financial_institution_provider_types`.

# `financial_institutions`

## Назначение

Справочник финансовых организаций и провайдеров: банки, брокеры, эмитенты карт, криптобиржи, провайдеры кошельков, платежные сервисы и кредиторы.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ провайдера. |
| `name` | VARCHAR | Нормализованное название провайдера. |
| `country` | VARCHAR | Основная страна или юрисдикция провайдера. |
| `website_url` | VARCHAR | Официальный сайт провайдера. |
| `logo_url` | VARCHAR | URL логотипа для интерфейса. |
| `integration_key` | VARCHAR | Ключ провайдера во внешнем API открытого банкинга, банковском коннекторе или интеграции. |
| `risk_level` | VARCHAR | Внутренний индикатор риска: `low`, `medium`, `high`, `unknown`. |
| `is_active` | BOOLEAN | Признак того, что провайдер активен и доступен для выбора/интеграции. |

## Подробное описание

Эта таблица нужна, чтобы не дублировать названия провайдеров в `accounts`, `liabilities` и будущих интеграционных таблицах. В `accounts.institution_name` и `liabilities.creditor_name` можно временно хранить сырое название, если нормализация еще не выполнена.

---

# `financial_institution_provider_types`

## Назначение

Связующая таблица многие-ко-многим между финансовыми провайдерами и их ролями.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `financial_institution_id` | UUID | FK -> `financial_institutions.id`. Указывает провайдера. |
| `provider_type_id` | UUID | FK -> `provider_types.id`. Указывает роль провайдера. |

## Подробное описание

Эта таблица позволяет одному провайдеру иметь несколько ролей. Например:

* Tinkoff -> `bank`
* Tinkoff -> `broker`
* Tinkoff -> `card_issuer`
* Binance -> `crypto_exchange`
* MetaMask -> `wallet_provider`

Для надежности стоит добавить уникальный индекс на пару `financial_institution_id`, `provider_type_id`.

Справочник типов долгов и обязательств.

# `accounts`

## Назначение

Хранит финансовые счета пользователя: банковские счета, карты, наличные, брокерские счета, криптокошельки и другие места хранения денег.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ счета. |
| `user_id` | UUID | FK -> `users.id`. Владелец счета. |
| `account_type_id` | UUID | FK -> `account_types.id`. Тип счета. |
| `institution_id` | UUID | Может быть пустым, FK -> `financial_institutions.id`. Нормализованный провайдер счета. |
| `name` | VARCHAR | Пользовательское название счета, например "Основная карта" или "Наличные". |
| `institution_name` | VARCHAR | Сырое или вручную введенное название провайдера, если `institution_id` пока неизвестен. |
| `currency` | VARCHAR | Валюта счета. |
| `balance` | DECIMAL | Текущий баланс счета. |
| `is_active` | BOOLEAN | Активен ли счет. Неактивные счета можно скрывать из основных сценариев, но сохранять для истории. |
| `created_at` | TIMESTAMP | Дата и время создания записи. |
| `updated_at` | TIMESTAMP | Дата и время последнего изменения записи. |

## Подробное описание

`accounts` описывает место, где находятся деньги или откуда приходят банковские операции. Кредитная карта может быть одновременно счетом и обязательством: в `accounts` она нужна как источник операций и баланс по банковской ленте, а в `liabilities` - как долг для анализа погашения.

Для крипты `account_type_id` описывает форму счета, например `crypto_wallet`, а `institution_id` указывает провайдера: Binance, Coinbase, Ledger, MetaMask или провайдера некастодиального кошелька.

# `categories`

## Назначение

Единый справочник категорий доходов и расходов.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ категории. |
| `parent_id` | UUID | Может быть пустым, FK -> `categories.id`. Родительская категория для дерева категорий. |
| `type` | VARCHAR | Тип категории: `income` или `expense`. |
| `name` | VARCHAR | Название категории. |
| `description` | TEXT | Описание категории и правил классификации. |

## Подробное описание

Категории поддерживают иерархию: например, "Еда" -> "Рестораны", "Продукты", "Кофе". Доходы и расходы можно хранить в одном дереве, но поле `type` помогает не назначать расходную категорию доходной операции и наоборот.

# `transactions`

## Назначение

Главный журнал реальных денежных операций.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ операции. |
| `user_id` | UUID | FK -> `users.id`. Владелец операции. |
| `account_id` | UUID | FK -> `accounts.id`. Счет, по которому прошла операция. |
| `category_id` | UUID | Может быть пустым, FK -> `categories.id`. Категория операции. |
| `type` | VARCHAR | Тип операции: `income`, `expense`, `transfer`. |
| `amount` | DECIMAL | Сумма операции. Рекомендуется хранить положительное число, а направление определять через `type`. |
| `currency` | VARCHAR | Валюта операции. |
| `transaction_datetime` | TIMESTAMP | Дата и время операции. |
| `description` | TEXT | Описание пользователя или импортированное назначение платежа. |
| `merchant_id` | UUID | Может быть пустым, FK -> `merchants.id`. Нормализованный продавец или поставщик услуг. |
| `merchant_name` | VARCHAR | Сырое название продавца/источника из импорта. |
| `geo_location` | VARCHAR | Опциональная геолокация операции. |
| `recurring_transaction_id` | UUID | Может быть пустым, FK -> `recurring_transactions.id`. Шаблон регулярной операции, если операция была сопоставлена с паттерном. |
| `external_id` | VARCHAR | Внешний ID из банка или интеграции для дедупликации импортированных операций. |
| `created_at` | TIMESTAMP | Дата и время создания записи. |

## Подробное описание

`transactions` должен оставаться денежным журналом. Не нужно добавлять сюда поля, специфичные для долгов, например тело долга, проценты или остаток долга. Эти данные относятся к `liability_payments`.

Для банковского импорта важно иметь дедупликацию. Обычно `external_id` используется вместе с `account_id`, датой и источником интеграции. В будущем может понадобиться отдельная таблица импортов или поле `external_source`.

# `recurring_transactions`

## Назначение

Хранит шаблоны регулярных финансовых операций: подписки, зарплата, аренда, коммунальные платежи, плановые платежи по кредитам.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ регулярного паттерна. |
| `user_id` | UUID | FK -> `users.id`. Владелец паттерна. |
| `account_id` | UUID | FK -> `accounts.id`. Счет списания или зачисления. |
| `category_id` | UUID | Может быть пустым, FK -> `categories.id`. Ожидаемая категория операций по этому паттерну. |
| `liability_id` | UUID | Может быть пустым, FK -> `liabilities.id`. Заполняется, если регулярный платеж связан с долгом. |
| `operation_type` | VARCHAR | Тип ожидаемой операции: `income`, `expense`, `transfer`, `liability_payment`. |
| `name` | VARCHAR | Название паттерна, например "Ипотека" или "Netflix". |
| `expected_amount` | DECIMAL | Ожидаемая сумма. Может отличаться от фактической суммы операции. |
| `currency` | VARCHAR | Ожидаемая валюта. |
| `frequency` | VARCHAR | Частота: `daily`, `weekly`, `monthly`, `yearly`. |
| `interval_count` | INTEGER | Интервал повторения. Например, `2` + `weekly` означает раз в две недели. |
| `day_of_month` | INTEGER | День месяца для месячных платежей. |
| `start_date` | DATE | Дата начала паттерна. |
| `end_date` | DATE | Опциональная дата окончания паттерна. |
| `next_payment_date` | DATE | Следующая ожидаемая дата платежа. |
| `auto_generated` | BOOLEAN | Создан ли паттерн автоматически, например AI/ML-детектором. |
| `confidence_score` | DECIMAL | Уверенность автоматического определения. |
| `is_active` | BOOLEAN | Активен ли паттерн. |

## Подробное описание

Это не фактические операции. Фактическая операция создается в `transactions`, а потом может ссылаться на `recurring_transactions`.

Для долгов используется `operation_type = liability_payment` и `liability_id`. Например, ипотека хранится как `liabilities`, ее ежемесячный график - как `recurring_transactions`, а каждый реальный платеж - как `transactions` + `liability_payments`.

# `transfers`

## Назначение

Хранит переводы между собственными счетами пользователя.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ перевода. |
| `user_id` | UUID | FK -> `users.id`. Владелец перевода. |
| `from_account_id` | UUID | FK -> `accounts.id`. Счет-источник. |
| `to_account_id` | UUID | FK -> `accounts.id`. Счет-получатель. |
| `amount` | DECIMAL | Сумма перевода. |
| `currency` | VARCHAR | Валюта перевода. |
| `transaction_datetime` | TIMESTAMP | Дата и время перевода. |
| `description` | TEXT | Описание перевода. |

## Подробное описание

Переводы не должны попадать в расходы или доходы пользователя. На уровне реализации нужно выбрать один консистентный подход:

* хранить перевод только в `transfers` и учитывать его отдельно;
* или хранить `transfers` как бизнес-сущность, а в `transactions` создавать две связанные операции: списание и зачисление.

Второй подход удобнее для восстановления балансов счетов.

# `asset_types`

## Назначение

Справочник типов активов.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ типа актива. |
| `code` | VARCHAR | Стабильный машинный код, например `real_estate` или `stocks`. |
| `name` | VARCHAR | Название для интерфейса. |
| `description` | TEXT | Описание типа актива. |

## Примеры значений

* `real_estate`
* `car`
* `crypto`
* `stocks`
* `business`
* `gold`

## Подробное описание

Тип актива лучше хранить справочником, а не свободным текстом. Это позволяет корректно считать структуру капитала и строить рекомендации по диверсификации.

# `assets`

## Назначение

Хранит активы и имущество пользователя для расчета чистого капитала.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ актива. |
| `user_id` | UUID | FK -> `users.id`. Владелец актива. |
| `asset_type_id` | UUID | FK -> `asset_types.id`. Тип актива. |
| `name` | VARCHAR | Название актива, например "Квартира", "Автомобиль", "Портфель IBKR". |
| `estimated_value` | DECIMAL | Текущая оценочная стоимость актива. |
| `currency` | VARCHAR | Валюта оценки. |
| `purchase_price` | DECIMAL | Цена покупки. |
| `purchase_date` | DATE | Дата покупки. |
| `monthly_cost` | DECIMAL | Ежемесячная стоимость обслуживания актива. |
| `created_at` | TIMESTAMP | Дата и время создания записи. |
| `updated_at` | TIMESTAMP | Дата и время последнего изменения записи. |

## Подробное описание

`assets` хранит текущую оценку, но не историю переоценки. Если продукт будет показывать динамику стоимости имущества, стоит добавить отдельную таблицу истории оценок, например `asset_valuations`.

# `liabilities`

## Назначение

Хранит кредиты, долги и другие финансовые обязательства пользователя.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ обязательства. |
| `user_id` | UUID | FK -> `users.id`. Владелец обязательства. |
| `liability_type_id` | UUID | FK -> `liability_types.id`. Тип обязательства. |
| `linked_account_id` | UUID | Может быть пустым, FK -> `accounts.id`. Связанный счет, если долг импортирован как банковский/карточный счет. |
| `collateral_asset_id` | UUID | Может быть пустым, FK -> `assets.id`. Актив-залог для обеспеченного долга. |
| `name` | VARCHAR | Название долга для пользователя. |
| `creditor_institution_id` | UUID | Может быть пустым, FK -> `financial_institutions.id`. Нормализованный кредитор. |
| `creditor_name` | VARCHAR | Сырое или вручную введенное название кредитора. |
| `original_amount` | DECIMAL | Изначальная сумма долга. |
| `current_balance` | DECIMAL | Текущий остаток долга. |
| `currency` | VARCHAR | Валюта обязательства. |
| `interest_rate` | DECIMAL | Годовая номинальная процентная ставка. |
| `interest_type` | VARCHAR | Тип ставки: `fixed`, `variable`, `promotional`, `none`. |
| `minimum_payment_amount` | DECIMAL | Минимальный обязательный платеж, если известен. |
| `regular_payment_amount` | DECIMAL | Обычный плановый платеж. |
| `payment_due_day` | INTEGER | День месяца, когда обычно нужно платить. |
| `start_date` | DATE | Дата начала обязательства. |
| `maturity_date` | DATE | Ожидаемая дата полного погашения. |
| `status` | VARCHAR | Статус: `active`, `paid_off`, `defaulted`, `refinanced`, `closed`. |
| `created_at` | TIMESTAMP | Дата и время создания записи. |
| `updated_at` | TIMESTAMP | Дата и время последнего изменения записи. |

## Подробное описание

`liabilities` хранит сам объект долга и его текущее состояние. Это не регулярный платеж и не денежная операция.

Связь с регулярными платежами строится через `recurring_transactions.liability_id`. Связь с фактическими платежами строится через `liability_payments.liability_id`.

Кредитные карты лучше моделировать осторожно: карта может быть `account`, потому что по ней приходят операции, и одновременно `liability`, потому что у нее есть долг, минимальный платеж и процентная ставка.

# `liability_payments`

## Назначение

Хранит фактические платежи по обязательствам и связывает их с денежными операциями.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ платежа по обязательству. |
| `user_id` | UUID | FK -> `users.id`. Владелец платежа. |
| `liability_id` | UUID | FK -> `liabilities.id`. Долг, по которому совершен платеж. |
| `transaction_id` | UUID | FK -> `transactions.id`. Денежная операция списания. |
| `recurring_transaction_id` | UUID | Может быть пустым, FK -> `recurring_transactions.id`. Регулярный паттерн, если платеж был плановым. |
| `payment_date` | DATE | Дата платежа. |
| `total_amount` | DECIMAL | Общая сумма платежа. |
| `principal_amount` | DECIMAL | Часть платежа, которая уменьшает тело долга. |
| `interest_amount` | DECIMAL | Процентная часть платежа. |
| `fee_amount` | DECIMAL | Комиссии, штрафы или пени. |
| `currency` | VARCHAR | Валюта платежа. |
| `balance_after_payment` | DECIMAL | Остаток долга после платежа. |
| `created_at` | TIMESTAMP | Дата и время создания записи. |

## Подробное описание

Эта таблица нужна, чтобы не терять структуру долгового платежа. Обычная операция в `transactions` показывает, что деньги ушли со счета. `liability_payments` объясняет, какая часть уменьшила тело долга, какая ушла на проценты, а какая на комиссии.

Для MVP, если разбиение неизвестно, можно временно записывать всю сумму в `principal_amount`, а затем уточнять после импорта от кредитора или ручной корректировки.

Хранит финансовые цели пользователя.

| ---- | --- | -------- |
| `id` | UUID | Первичный ключ цели. |

| `name` | VARCHAR | Название цели. |

# `merchants`

## Назначение

Справочник продавцов, сервисов и поставщиков услуг.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ продавца. |
| `name` | VARCHAR | Нормализованное название продавца. |
| `category` | VARCHAR | Основная категория продавца. |
| `country` | VARCHAR | Страна продавца или основная страна присутствия. |
| `risk_level` | VARCHAR | Индикатор риска или спорности продавца. |

## Подробное описание

`transactions.merchant_name` хранит сырое название из импорта, а `merchant_id` указывает на нормализованного продавца, если сопоставление удалось.

В будущем категорию продавца лучше связать с `categories`, но для первой версии можно оставить текстовое поле.

# `tags`

## Назначение

Хранит пользовательские теги для ручной разметки операций.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ тега. |
| `user_id` | UUID | FK -> `users.id`. Владелец тега. |
| `name` | VARCHAR | Название тега. |

## Подробное описание

# `transaction_tags`

## Назначение

Связующая таблица многие-ко-многим между операциями и тегами.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `transaction_id` | UUID | FK -> `transactions.id`. Операция. |
| `tag_id` | UUID | FK -> `tags.id`. Тег. |

## Подробное описание

Одна операция может иметь несколько тегов, и один тег может быть применен к множеству операций. Для защиты от дублей стоит добавить уникальный индекс на пару `transaction_id`, `tag_id`.

# `daily_financial_snapshots`

## Назначение

Хранит ежедневные агрегированные снимки финансового состояния пользователя.

## Поля

| Поле | Тип | Значение |
| ---- | --- | -------- |
| `id` | UUID | Первичный ключ снимка. |
| `user_id` | UUID | FK -> `users.id`. Владелец снимка. |
| `snapshot_date` | DATE | Дата снимка. |
| `total_cash` | DECIMAL | Общая ликвидная сумма на дату снимка. |
| `total_assets` | DECIMAL | Общая стоимость активов. |
| `total_liabilities` | DECIMAL | Общая сумма обязательств. |
| `net_worth` | DECIMAL | Чистый капитал: активы минус обязательства. |
| `monthly_income` | DECIMAL | Доход за текущий месяц на дату снимка. |
| `monthly_expenses` | DECIMAL | Расходы за текущий месяц на дату снимка. |
| `savings_rate` | DECIMAL | Доля сбережений. |

## Подробное описание

Эта таблица хранит рассчитанные значения для быстрых графиков, отчетов и прогнозов. Она не должна быть источником истины. Источником истины остаются `accounts`, `transactions`, `assets`, `liabilities` и платежные таблицы.

Для надежности стоит добавить уникальный индекс на пару `user_id`, `snapshot_date`.

# Открытые вопросы для следующего этапа

* Нужны ли отдельные таблицы для обменных курсов и мультивалютной переоценки.
* Нужно ли хранить историю балансов счетов отдельно от дневных агрегатов.
* Как будет устроена дедупликация банковского импорта: только `external_id` или отдельная таблица импортированных записей.
* Нужны ли семейные профили, если один финансовый профиль ведут несколько пользователей.
* Нужно ли добавить историю оценок активов, например `asset_valuations`.
* Нужно ли добавить историю изменения баланса обязательств, если кредитор присылает остатки без платежной детализации.
